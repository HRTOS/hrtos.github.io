01

理解等待机制

应用层描述需求，内核管理任务状态

实时任务并不总是需要持续运行。当任务等待某个时间点、 同步条件或通信数据时，合理的等待机制可以减少无效轮询， 让任务在适当的时机重新参与调度。

HRTOS 的等待子系统提供内核级等待状态管理。 应用程序应优先使用项目实际提供的延时、同步与通信接口， 而不是自行修改任务状态、等待计数或资源等待位图。

使用原则

应用层关注等待条件与返回结果，内核负责等待上下文和任务状态管理。 高级接口是否使用统一的 os_wait() 路径，应以各模块的实际实现为准。

02

常见等待场景

先区分等待的目标，再选择对应接口

TIME

延时等待

任务需要延后执行、周期性工作或等待一段时间后再次检查条件时使用。

重点：时间单位、零值语义与实际延时路径
SYNCHRONIZATION

同步等待

任务需要等待某项同步条件或共享资源状态发生变化时， 使用项目实际提供的同步接口。

重点：获取条件、等待结果与资源释放规则
MESSAGING

消息等待

任务需要发送或接收任务间消息时，遵循消息模块规定的队列和阻塞语义。

重点：队列容量、发送接收结果与超时策略
EVENT

事件等待

任务需要等待特定事件或通知时，使用事件模块提供的接口与结果定义。

重点：事件条件、触发时机与等待结束原因
接口名称以实际头文件为准

本页不将信号量、互斥锁、消息队列、事件和邮箱的接口名或参数顺序 作为未经核实的固定 API。编写应用程序前，请先查阅当前 HRTOS 版本 对应的头文件与 API 文档。

03

延时等待

等待时间不是忙循环次数

延时适用于周期性任务、分阶段处理以及暂时不需要继续执行的场景。 使用前，应确认延时接口的参数单位、时间精度和边界条件， 并确保所使用的接口确实适用于当前任务类型。

Usage Pattern Pseudocode 
任务循环
    │
    ├─ 执行业务处理
    │
    ├─ 调用项目提供的延时接口
    │
    └─ 延时结束后继续执行

对于普通任务，已提供的内核实现表明， WAIT_DELAY 会走独立的延时分支，并记录普通任务的等待上下文。 高速任务的延时则有专门处理路径，因此不能假设所有任务类型 都使用完全相同的等待存储方式。

周期任务的注意事项

如果任务要求稳定周期，应进一步评估任务执行时间、延时语义、 Tick 分辨率与调度抖动。简单地在任务末尾增加固定延时， 不一定能保证严格的固定周期。

04

同步等待

等待条件与等待结果必须一起考虑

当任务需要等待同步条件时，应用程序应使用对应同步模块的公开接口。 不应直接修改内核等待标志，也不应将内部等待类型宏当成应用层 API 使用。

Conceptual Flow Not API Code 
尝试执行同步操作
        │
        ├─ 条件满足
        │    └─ 按接口约定继续处理
        │
        └─ 需要等待
             └─ 按接口约定阻塞或返回
                    │
                    └─ 等待结束后检查结果

信号量与互斥锁虽然都可能涉及等待， 但它们表达的语义不同：信号量通常用于同步或资源计数， 互斥锁用于保护需要互斥访问的共享资源。 不能仅因为两者可能进入 WAIT 状态，就把它们当成可互换的接口。

不要推断未确认的内核特性

优先级继承、递归加锁、超时锁定、ISR 中的可调用限制等， 都应依据实际实现与接口说明确认，不能仅从“支持互斥锁”这一点推导出来。

05

消息与事件等待

使用模块提供的发送、接收与通知接口

消息与事件通常用于任务间解耦：一个任务产生数据或通知， 另一个任务在需要时等待并处理。应用程序应依据对应模块的契约， 处理发送失败、接收结果、超时和事件条件等情况。

MESSAGE SEND

发送消息

确认目标队列、消息格式、队列容量以及队列不可接收新消息时的处理规则。

MESSAGE RECEIVE

接收消息

确认队列为空时接口如何处理，以及返回值如何区分收到消息与未收到消息。

EVENT

事件通知

确认事件条件、事件清除规则、重复触发行为与等待结束的语义。

MAILBOX

邮箱通信

如当前版本提供邮箱接口，应根据对应 API 文档确认数据传递与阻塞规则。

不要忽略返回值

等待结束只说明阻塞阶段结束，不一定意味着消息已经成功发送、 数据已经成功接收，或者业务条件一定成立。应按照具体 API 的返回语义 决定下一步处理。

06

超时与返回结果

等待结束后，明确判断为什么结束

对具有超时能力的接口，应区分正常完成、等待超时以及接口定义的其他结果。 不同模块的结果类型可能不同，必须以该接口的文档和宏定义为准。

调用等待类 API 按接口约定传入参数
↓
等待结束 可能由条件满足、超时或其他定义的结果结束
↓
检查接口返回结果 只在确认结果后继续对应的业务操作
  • 确认超时参数使用的时间单位及其边界语义。
  • 确认超时后资源是否仍可能被其他任务获取。
  • 确认接口返回值是否需要进一步读取结果数据。
  • 避免将“任务恢复执行”误判为“等待条件已经满足”。

关于内核的 wait_tick、 wait_flag 与 wake_task() 的具体关系， 请参阅等待超时与状态模型文档；应用层不应自行模拟这套内部状态管理。

应用层设计示例

用明确的业务结构表达等待逻辑

以下是与具体 HRTOS API 无关的伪代码，用于展示任务的业务组织方式。 实际项目中应将占位步骤替换为当前版本真实存在的接口， 并按照接口返回值补全错误处理。

Application Structure Pseudocode 
void application_task(void)
{
    for (;;)
    {
        /* 1. 执行本轮业务准备 */

        /* 2. 使用项目实际提供的等待接口 */

        /* 3. 根据接口返回值判断结果 */

        /* 4. 仅在条件满足时处理对应业务数据 */

        /* 5. 进入下一轮任务处理 */
    }
}
为什么这里使用伪代码？

当前页面未提供同步、消息和事件模块的实际头文件。 与其写入可能不符合 HRTOS 当前版本的函数签名， 不如先明确使用结构，避免示例被直接复制后产生编译错误或语义误用。

08

应用层使用准则

减少误用，并保持接口与内核边界清晰

  • 优先使用公开的应用层 API，不直接修改内核等待结构。
  • 每次等待都应有明确目的：等待时间、同步条件、消息或事件。
  • 使用超时功能时，明确规定超时后的业务处理策略。
  • 根据接口契约检查返回值，不把唤醒等同于操作成功。
  • 确认哪些接口可以在中断服务程序中调用，哪些只能在任务上下文使用。
  • 结合任务优先级、执行时间与等待关系，检查潜在的死锁和长期阻塞。
  • 以当前 HRTOS 版本的头文件和 API 文档为最终依据。
09

总结

应用层使用简单，底层机制保持一致性

等待机制的价值不只是让任务暂停执行，而是为任务之间的时间安排、 同步关系和通信行为提供清晰的控制方式。 应用程序应通过公开接口表达等待需求， 并在等待结束后依据返回结果决定下一步操作。

对于内核实现，应进一步阅读等待上下文、超时处理、任务状态模型和调度流程； 对于应用开发，则应重点关注 API 契约、错误处理、超时语义和任务间依赖关系。 两个层次各自清晰，才能使系统更容易验证与维护。
