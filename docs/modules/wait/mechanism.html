Wait Mechanism 任务等待与唤醒机制

从实际内核实现出发，说明 os_wait() 如何记录等待上下文、将普通任务移出就绪集合， 以及 wake_task() 如何清理等待信息、设置唤醒结果并恢复任务的调度资格。

os_wait() wake_task() Wait Context Resource Bitmap Task State
01

机制概览

统一等待上下文，分别处理普通任务与高速任务

HRTOS 通过 os_wait() 建立任务等待状态，通过 wake_task() 恢复普通任务的就绪资格。 对普通任务，等待上下文记录在 OS_TASK[tid] 中； 对两个高速任务的延时等待，源码使用独立的计数器路径。

普通任务路径

记录等待类型、对象、Tick 和结果；资源等待时更新资源位图； 将任务状态设为 WAIT，并清除 OS_PROCESS_OK[tid] 的最低位，随后请求调度。

高速任务延时路径

当 type == WAIT_DELAY 且任务编号属于两个高速任务时， 使用 OS_WAIT_DI2[0] 或 OS_WAIT_DI2[1] 保存延时计数，并请求 T0 中断。 该分支不建立普通任务的等待上下文。

关键区别： 等待状态、任务调度资格和唤醒结果是相互关联但不同的概念。 state = WAIT 表示任务状态； OS_PROCESS_OK 的最低位控制其调度资格； wait_flag 保存普通任务最终观察到的等待结果。
02

等待上下文

四个字段记录一次普通任务等待所需的信息

在提供的实现中，等待上下文直接保存在 OS_TASK[tid] 对应的任务记录中。 以下字段名称来自实际调用代码，不是另行定义的示意性 TCB。

字段 作用 设置与清理
wait_type 标识当前等待类型；WAIT_NONE 用于判断普通任务是否已有等待上下文。 进入等待时写入 type；唤醒时恢复为 WAIT_NONE。
wait_obj 记录等待对象编号，延时等待可以不关联有效资源对象。 进入等待时写入 obj；唤醒时恢复为 OS_INVALID_ID。
wait_tick 记录以系统 Tick 为单位的等待时间参数。 进入等待时写入 tick；唤醒时清零。
wait_flag 保存等待结果，源码注释列出了 WAIT_TIMEOUT 与 WAIT_SIGNAL。 进入普通等待时初始化为 0；唤醒时写入传入的 flag。
等待上下文的实际使用方式 wait.c / wake_task.c 
/* os_wait(): 建立等待上下文 */
OS_TASK[tid].wait_type = type;
OS_TASK[tid].wait_obj  = obj;
OS_TASK[tid].wait_tick = tick;
OS_TASK[tid].wait_flag = 0;

/* wake_task(): 清理等待上下文 */
OS_TASK[tid].wait_type = WAIT_NONE;
OS_TASK[tid].wait_obj  = OS_INVALID_ID;
OS_TASK[tid].wait_tick = 0;

唤醒时，wait_flag 不会被清零，而是先被写入本次唤醒原因。 因此，在普通任务恢复运行并从等待调用返回时，可以通过返回值识别等待结果。

03

普通任务如何进入等待

os_wait() 的执行顺序

对普通任务，os_wait() 在进入关键状态更新前关闭总中断， 完成等待上下文和相关调度信息的修改后，再恢复总中断并请求 T0 中断。

进入临界区并获取当前任务 ID

执行 EA = 0，读取 OS_CURRENT_TASK。

02
检查等待上下文与资源编号

对非延时等待，若 wait_type != WAIT_NONE，返回 0； 若 obj >= OS_RESOURCE_MAX，同样返回 0。

↓
03
写入等待上下文

保存 type、obj、tick， 并将 wait_flag 初始化为 0。

↓
04
必要时登记资源等待关系

当 type != WAIT_DELAY 且 obj != OS_INVALID_ID 时，设置资源等待位图中的任务位， 并递增该资源的 wait_cnt。

↓
05
阻塞当前任务并请求调度

设置 state = WAIT，清除 OS_PROCESS_OK[tid] 的最低位， 并将 OS_SCHED_REASON 设为 1。

↓
06
退出临界区，触发 T0 中断

执行 EA = 1，随后设置 TF0 = 1， 请求系统进入后续调度处理。

不要混淆请求与执行： OS_SCHED_REASON = 1 和 TF0 = 1 是调度请求路径中的操作；不能据此认为 os_wait() 在当前函数体内直接完成了上下文切换。
04

资源等待位图

通过 wait_mask 记录任务与资源之间的等待关系

当普通任务执行非延时等待，且等待对象不是 OS_INVALID_ID 时，内核使用资源记录中的 wait_mask 和 wait_cnt 登记等待关系。

登记等待关系 wait.c 
if(type != WAIT_DELAY && obj != OS_INVALID_ID)
{
    OS_RES[obj].wait_mask |= ((u16)1 << tid);
    OS_RES[obj].wait_cnt++;
}
清除等待关系 wake_task.c 
if(obj != OS_INVALID_ID)
{
    OS_RES[obj].wait_mask &= ~((u16)1 << tid);

    if(OS_RES[obj].wait_cnt)
    {
        OS_RES[obj].wait_cnt--;
    }
}
成员 实现行为 理解要点
wait_mask 使用 (u16)1 << tid 设置或清除对应任务位。 位图记录任务是否登记在该资源的等待集合中。
wait_cnt 登记时递增；唤醒清理时，在计数非零的情况下递减。 它是等待数量的辅助记录，维护正确性依赖调用路径与等待关系保持一致。
OS_INVALID_ID 该对象值不会触发上述资源位图访问。 等待上下文可以不关联需要登记的资源对象。
实现边界： wake_task() 在检查任务是否已删除或处于 DEAD 状态之前，就执行等待位图清理和计数处理。 此外，当前代码只在 wait_cnt 非零时递减，并没有在递减前检查 对应任务位是否原本已置位。因此，调用方应避免重复唤醒或不匹配的清理操作， 并确保资源等待记录的一致性。
05

任务唤醒与恢复调度

wake_task() 的真实处理顺序

wake_task(tid, flag) 接收目标任务 ID 和唤醒结果。 在临界区内，它先读取任务记录中的等待对象，再清理可能关联的资源等待记录， 然后判断目标任务是否仍允许唤醒。

01
关闭总中断并读取等待对象

执行 EA = 0，将 wait_obj 保存到局部变量 obj。

↓
02
清理资源等待位图

当 obj != OS_INVALID_ID 时，清除对应任务位， 并在计数非零时递减 wait_cnt。

↓
03
检查任务是否需要跳过唤醒

若 OS_PROCESS_OK[tid] == 0，或 state == DEAD，则恢复总中断并直接返回。

↓
04
记录唤醒结果并清理上下文

写入 wait_flag = flag，将 wait_type 设为 WAIT_NONE， 将对象设为 OS_INVALID_ID，并将等待 Tick 清零。

↓
05
恢复就绪状态和调度资格

设置 state = READY，通过 OS_PROCESS_OK[tid] |= 1 恢复最低位， 并设置 OS_SCHED_REASON = 1。

↓
06
恢复总中断并请求 T0 中断

执行 EA = 1，然后设置 TF0 = 1。

唤醒不等于立即运行： wake_task() 恢复的是任务的就绪状态和调度资格，并请求重新调度。 任务何时真正获得 CPU，仍取决于系统的调度处理。
06

等待结果与返回语义

区分零 Tick 延时、参数错误与被唤醒后的结果

场景 源码行为 返回值理解
WAIT_DELAY 且 tick == 0 立即恢复总中断并返回，不建立等待上下文。 直接返回 WAIT_TIMEOUT。
普通任务进入等待 先将 wait_flag 初始化为 0，再请求调度。 任务恢复执行后，等待调用通过 wait_flag 返回结果。
资源编号越界 非延时等待且 obj >= OS_RESOURCE_MAX 时返回。 返回 0。
普通任务已有等待上下文 非延时分支检测到 wait_type != WAIT_NONE 时返回。 返回 0。
高速任务的延时分支 使用独立计数器，设置调度请求并触发 T0 中断。 该分支在设置延时计数后直接返回 WAIT_TIMEOUT；不能套用普通任务的阻塞返回过程来解释。
关于返回值： 在普通任务路径中，wait_flag 初始化为 0，而函数源码在阻塞请求之后返回该字段。 结合任务切换机制，应将其理解为任务恢复执行后读取的等待结果，而不是把函数调用点之后的代码理解为必然立即执行。 对高速任务的延时分支，源码行为不同，应单独描述。

wake_task() 本身只负责写入调用方传入的 flag，并不在该函数中判断该标志代表超时还是信号。 超时与正常唤醒的具体分类，应结合调用 wake_task() 的代码路径及相应标志定义确认。

07

高速任务的延时路径

独立计数，不使用普通任务等待上下文

os_wait() 首先处理 WAIT_DELAY。 如果当前任务编号大于或等于 OS_PROCESS_MAX， 则进入高速任务专用分支，而不是继续执行普通任务的等待上下文和资源登记流程。

高速任务延时处理 wait.c 
if(tid == OS_PROCESS_MAX)
{
    OS_KUAI_PROCESS_A = 0;
    OS_WAIT_DI2[0] = tick;
    OS_SCHED_REASON = 1;
    EA = 1;
    TF0 = 1;
}
else if(tid == OS_PROCESS_MAX + 1)
{
    OS_KUAI_PROCESS_B = 0;
    OS_WAIT_DI2[1] = tick;
    OS_SCHED_REASON = 1;
    EA = 1;
    TF0 = 1;
}

return WAIT_TIMEOUT;
  • 高速任务 A 使用 OS_WAIT_DI2[0] 保存延时计数。
  • 高速任务 B 使用 OS_WAIT_DI2[1] 保存延时计数。
  • 该分支清除对应高速任务标志，设置调度请求并触发 T0 中断。
  • 该路径没有设置普通任务的 wait_type、wait_obj、wait_tick 和 wait_flag。
文档边界： 这里描述的是 wait.c 中能够直接确认的操作。 高速任务计数如何递减、何时重新获得执行资格，以及 T0 中断中的具体处理， 应由对应的计时与调度源码进一步说明。
08

实现要点与阅读边界

从源码理解机制，而不是将概念模型当成实现细节

统一的普通任务等待上下文

普通任务通过同一组等待字段记录等待状态、等待对象、时间参数和唤醒结果， 并由 wait_type 与 WAIT_NONE 表达是否存在活动等待上下文。

资源等待关系使用位图表示

wait_mask 通过任务 ID 对应的位记录资源等待关系； wait_cnt 作为计数辅助信息。位图的更新与任务唤醒路径需要保持一致。

任务状态与调度资格分别更新

阻塞时，内核同时设置 state = WAIT 并清除 OS_PROCESS_OK[tid] 的最低位；唤醒时则设置 state = READY 并恢复该位。理解这两个操作的配合， 有助于区分任务状态管理和调度资格管理。

临界区保护与调度请求

两个函数均在修改关键任务信息时使用 EA = 0， 完成主要状态更新后恢复总中断，并通过 TF0 = 1 请求后续处理。精确的上下文切换时刻应结合 T0 中断与调度器实现分析。

源码审阅提示： wake_task() 假定传入的 tid 是有效任务编号； 所给代码没有在访问 OS_TASK[tid] 前进行边界检查。 如果要从健壮性角度继续审计，应结合所有调用点确认参数约束。 同样，EA 在进入函数前的状态没有被保存并恢复，而是在路径中直接设为 1； 这属于中断状态管理的独立审阅点，不应与等待机制的正常流程混为一谈。
