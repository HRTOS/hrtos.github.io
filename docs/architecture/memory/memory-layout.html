内存布局 Memory Layout

内存布局描述系统运行所依赖的存储区域、地址空间与运行时数据的组织关系。 对资源受限的 8051 系统而言，布局不仅影响变量与栈的放置， 还会影响上下文保存、函数调用、中断处理以及内核资源的可用边界。

01 / OVERVIEW

内存布局要回答什么问题？

内存布局不是简单地把系统划分成几个连续区间，而是明确不同数据存放在哪里、 由谁使用，以及这些存储资源受到什么限制。

01

地址空间与存储能力

明确芯片支持的内部 RAM、外部数据存储空间、寄存器组及其寻址方式， 避免将逻辑用途与物理地址空间混为一谈。

Address Space · Capacity · Access
02

运行时数据组织

梳理任务控制信息、上下文、栈、队列及全局数据的组织方式， 识别它们之间的容量约束和使用关系。

Task Context · Stack · Kernel Data
03

资源使用边界

明确哪些区域由硬件、编译器、内核或应用代码使用， 并识别共享存储、栈深度和内存不足带来的风险。

Ownership · Allocation · Limits
04

运行行为与可分析性

让关键数据的容量、访问方式与生命周期能够被检查， 为上下文切换分析、栈预算和最坏执行时间分析提供基础。

Stack Budget · Timing · Verification
02 / MEMORY MODEL

8051 存储结构与运行时区域

理解 HRTOS 的内存布局，需要区分 8051 的硬件存储空间与操作系统层面的逻辑区域。 两者有关联，但并不是一一对应的关系。

硬件存储与软件用途的关系示意 逻辑示意 · 非实际地址映射图
DATA
直接寻址内部数据区 容量与可用地址取决于具体 8051 兼容芯片及地址映射
IDATA
间接寻址内部数据区 用于可间接寻址的内部 RAM；与 DATA 的地址范围存在体系结构关系
SFR
特殊功能寄存器 包含 CPU、定时器、中断控制等硬件寄存器；不是普通 RAM
XDATA
外部数据存储空间 实际容量取决于芯片实现、存储配置、链接布局及系统预留
RUNTIME
任务栈、上下文、内核对象与应用数据 属于软件用途分类，具体放置位置由 HRTOS 实现、编译器和目标配置共同决定

注意：DATA、IDATA、SFR 和 XDATA 是 8051 体系结构中的存储或寻址概念； 任务栈、上下文、队列与内核对象则是软件运行时用途。 不应将它们直接画成互不重叠、具有固定先后顺序的物理内存分区。

03 / REGION RESPONSIBILITIES

关键运行时区域

以下按软件职责说明常见区域。实际项目中，某类数据可能分散在不同地址空间， 也可能由静态分配、专用内存池或编译器机制管理。

区域或对象 主要用途 需要关注的约束
CPU 寄存器组 保存处理器当前工作状态；8051 的寄存器组选择与 PSW 等硬件状态有关。 寄存器组分配、中断使用规则、任务切换时的状态保护。
硬件堆栈 通过 SP 管理压栈和出栈，常用于返回地址及部分现场保存。 初始 SP、最大压栈深度、中断嵌套、函数调用与其他内部 RAM 使用之间的冲突。
任务上下文 保存恢复任务运行所需的寄存器、栈指针或其他调度状态。 上下文格式、保存恢复顺序、每任务开销和切换路径的一致性。
任务栈与调用栈 支撑函数调用、局部变量及运行时保存操作；具体机制依赖内核与编译器实现。 栈深度、嵌套调用、重入性、中断现场和栈空间预算。
内核控制数据 保存任务状态、调度信息、队列索引、资源管理数据等。 固定容量、数组边界、共享访问、中断并发及内存占用。
消息队列与资源池 管理任务间通信对象及可复用资源。 对象数量上限、单对象大小、分配失败行为和生命周期。
应用静态数据 保存全局变量、静态变量及应用长期状态。 全局内存预算、共享变量访问、中断可见性和数据一致性。
04 / DESIGN PRINCIPLES

内存布局的工程原则

对小 RAM 微控制器而言，内存布局不仅要满足“能够运行”，还要让资源使用可检查、 关键路径的开销可估算，以及容量不足时的行为可识别。

PRINCIPLE / 01

容量有边界

对任务数、队列数、资源池和上下文存储设置明确的容量约束， 并在构建或运行阶段检查相关限制。

PRINCIPLE / 02

栈空间可预算

结合调用深度、中断嵌套、现场保存和任务切换路径估算栈需求， 避免仅凭正常运行时的观察判断栈是否充足。

PRINCIPLE / 03

布局可验证

通过编译器内存报告、链接映射文件、反汇编和压力测试， 核对实际布局与设计假设是否一致。

05 / ENGINEERING WORKFLOW

从内存设计到验证

内存布局应由目标平台的实际配置与构建产物支撑，而不是仅凭示意图推断。

STEP 01 确认目标硬件

核对 RAM 容量、寻址空间、寄存器组和芯片扩展能力。

STEP 02 梳理软件对象

统计上下文、内核控制数据、队列、任务栈及应用变量。

STEP 03 检查构建布局

结合编译器报告、链接映射和实际地址分配检查占用。

STEP 04 验证运行边界

检查栈深度、容量上限、中断路径及资源不足时的行为。

06 / REAL-TIME IMPLICATIONS

内存布局与实时性

内存布局是分析运行时间和资源边界的重要基础，但布局清晰本身并不等于已经证明最坏执行时间或硬实时保证。

A

上下文切换开销

上下文保存与恢复涉及的数据量、访问方式及指令路径， 会影响任务切换的执行时间和内部存储占用。

B

中断与栈安全

中断现场、嵌套层级和任务运行状态共同影响栈预算。 必须结合真实调用路径和内核实现进行分析。

C

资源申请的时间行为

固定大小对象池与动态分配具有不同的时间和容量特征。 应根据实际分配算法及失败处理路径评估，而不能仅根据名称判断。

D

数据访问与共享

内存位置、寻址指令和共享访问方式可能改变代码路径及临界区需求， 需要结合编译结果与中断并发关系检查。

!

平台相关性说明

本页面介绍的是内存布局的架构分析方法，并不代表所有 HRTOS 目标板使用相同的地址分配。 具体区域、大小与访问约束应以对应芯片手册、HRTOS 版本配置、 Keil C51 编译设置及链接映射结果为准。
