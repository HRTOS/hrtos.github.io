IPC 模型 Inter-Task Communication Model

IPC 模型用于理解任务之间的数据交换、执行同步与资源协作。 本页从通信语义、对象状态和任务调度三个角度，建立阅读 HRTOS 通信机制的整体框架。

ARCHITECTURE / COMMUNICATION 从对象语义理解任务协作
01

模型概述

IPC 解决什么问题，以及为什么需要区分不同的通信语义。

在多任务系统中，各任务通常围绕各自的执行流程工作。 当任务之间需要传递数据、通知状态变化或协调共享资源时， 就需要明确的通信与同步规则。

IPC（Inter-Process Communication）是这类协作机制的统称。 在嵌入式 RTOS 中，具体对象可能采用不同的数据结构和状态管理方式； 它们的行为不能仅凭名称推断，而应结合接口定义与内核实现理解。

i

理解重点： IPC 不只是传递数据。等待条件、操作结果和任务状态的变化， 都可能影响系统的执行顺序；但并非每次通信操作都会发生任务切换。

02

通信语义分类

先判断需要解决的问题，再选择适当的机制。

01 / DATA

数据传递

关注数据如何从生产者交给消费者，是否需要缓冲、是否保留顺序， 以及数据积压时如何处理。

02 / EVENT

状态通知

关注某个条件是否发生、通知是否保留，以及接收任务如何判断 当前状态是否满足处理条件。

03 / SYNC

执行同步

关注任务之间的执行依赖、等待条件和唤醒规则， 避免依赖不明确的时序假设。

04 / RESOURCE

资源协调

关注共享资源的访问边界、获取与释放规则， 以及并发访问时可能产生的冲突。

!

上述分类描述的是通用设计语义，不等同于 HRTOS 4.0 的具体功能清单。 对象类型、接口签名和可调用上下文应以实际内核接口为准。

03

分层理解

将应用需求、通信对象与内核调度分开观察。

分层模型是一种用于阅读和分析系统的概念视图。 它帮助区分应用程序的通信意图、对象本身的语义，以及内核如何处理任务状态； 不意味着 HRTOS 内部一定采用完全对应的模块分层。

应用任务层

提出通信需求：传递数据、等待条件、通知状态或访问共享资源。

通信对象层

按对象语义处理数据、计数、状态或资源访问规则。

任务状态与调度

在具体内核规则下处理等待条件、任务就绪状态及后续执行顺序。

04

运行过程与调度关系

同一通信请求可能产生不同结果，不能假设固定的执行路径。

01

发起操作

任务请求执行通信操作，例如提交数据、检查通知或获取某种同步条件。

02

检查条件

根据对象语义判断操作是否可以完成、是否需要等待，或是否返回相应结果。

03

处理状态

内核可能更新对象状态，并根据操作结果与具体规则处理相关任务的等待状态。

04

继续执行

当前任务继续运行，或在符合内核调度条件时由其他就绪任务获得执行机会。

需要注意：通信完成不等于立即切换任务

操作可能立即成功，也可能失败或需要等待。即使某个等待条件满足， 实际调度时机仍取决于具体接口行为、任务优先级和内核调度规则。 本图表达的是概念关系，不是 HRTOS 源码的固定执行路径。

05

设计与实现边界

评估通信机制时，还需要考虑调用环境与资源限制。

任务上下文与中断上下文

不应假设任务上下文中可用的所有接口都能在中断服务程序中调用。 对可能阻塞或依赖任务调度的操作，必须确认内核对调用上下文的明确限制。

等待、超时与错误处理

设计应明确资源不可用时的行为、等待是否有界、超时后如何恢复， 以及调用方如何处理失败结果。不能仅凭对象名称推断这些能力。

优先级与实时性

IPC 本身并不能自动保证端到端响应时间。 还需要分析任务优先级、临界区、数据处理时间和系统负载。 优先级继承等具体策略必须以实际实现为依据。

内存与缓冲容量

对资源受限的 8051 系统，应评估通信对象的静态内存开销、 缓冲区大小和数据峰值，避免因缓存不足或资源占用影响系统稳定性。
