中断流模型（Interrupt Flow）

中断是处理器响应外部事件和内部时基的重要机制。 在实时操作系统中，中断处理不仅决定事件响应路径， 也会影响任务执行连续性、调度时机、上下文保护与最坏响应时间。

Interrupt Response Nested Interrupts Context Protection 8051 Architecture

核心定义

中断流描述从中断请求产生，到处理器接受请求、执行中断服务程序， 再到中断返回或进入后续内核处理路径的完整控制流。

对 RTOS 而言，中断是异步事件处理机制，也是影响系统响应时间的重要因素。 它可能改变任务执行的连续性，并在满足内核调度条件时影响后续任务选择。

因此，中断流分析需要同时考虑硬件响应行为、内核保护机制、 ISR 执行路径和中断退出语义。

Interrupt flow models the path from interrupt acceptance through ISR execution to return or subsequent kernel processing.

01. 中断请求与接受条件

中断请求可以来自定时器、外部引脚、串行通信接口及其他外设。 请求产生并不意味着处理器一定会立即执行对应的 ISR。

请求产生

外设事件发生并形成中断请求。具体请求标志、触发方式及清除规则 由芯片外设和中断控制机制决定。

请求接受

处理器根据中断使能、优先级、当前执行状态和架构规则， 判断何时能够响应请求。

中断屏蔽

全局中断关闭或相关中断被屏蔽时，请求的响应可能延迟。 延迟上界取决于屏蔽区间、请求行为和硬件规则。

请求积压与丢失

不同外设对待处理事件的记录能力不同。必须确认请求标志、 FIFO 或计数机制是否能保留连续发生的事件。

实时性分析不能只测量 ISR 的执行时间。 从事件发生到 ISR 开始执行之间的延迟，同样可能影响系统响应上界。

02. 中断响应路径

中断响应路径包含从请求等待到 ISR 开始执行的过程。 在经典 8051 及其兼容增强型芯片上，具体响应时序还取决于芯片内核、 指令边界、中断优先级和当前中断状态。

Interrupt Request 外设或定时器产生请求
↓
Acceptance Conditions 检查使能、屏蔽和优先级条件
↓
Hardware Entry 处理器进入中断入口
↓
ISR Prologue 执行入口代码及必要的上下文保护

在分析时，可以将响应时间拆分为请求等待、硬件接受与入口延迟， 以及 ISR 入口代码开始执行前的必要处理。 具体拆分边界应保持一致，避免同一开销重复计入。

Interrupt response latency and ISR execution time are distinct quantities and should be measured with clearly defined boundaries.

03. ISR 执行与上下文保护

ISR 执行期间，内核必须确保中断处理代码与被打断的任务、 其他中断路径之间不会发生未经处理的上下文破坏。

在 8051 架构上，这一问题尤其依赖寄存器组、堆栈、特殊功能寄存器 和编译器生成代码的具体使用方式。不能简单假定所有寄存器都会由硬件自动保存。

  • 确认硬件自动完成的中断入口操作与返回操作。
  • 确认 ISR 或内核入口代码需要保护的寄存器和状态。
  • 确认 ISR 使用的寄存器组与任务上下文之间的关系。
  • 核对编译器生成的 ISR 序言、尾声及调用约定。
  • 确认中断退出路径与内核要求的返回方式一致。
对 HRTOS 这样的 8051 内核，上下文保护是中断正确性的核心组成部分。 具体保存哪些寄存器、使用哪个寄存器组以及需要多少堆栈空间， 应以对应版本的汇编实现和编译结果为准。

04. 中断嵌套与优先级

中断嵌套指处理器在一个 ISR 尚未结束时，再接受另一个符合条件的中断请求。 是否允许嵌套、哪些中断能够嵌套，以及嵌套时采用什么上下文保护方式， 都由处理器架构与内核设计共同决定。

优先级规则

优先级影响中断接受与抢占关系，但高优先级请求能否立即执行， 还受到中断使能、屏蔽状态和架构规则的约束。

嵌套边界

可分析的嵌套行为需要明确允许的中断组合、最大嵌套深度 及各层入口和返回所需的资源。

堆栈预算

每增加一层嵌套，都可能增加返回地址、寄存器保存和局部调用的堆栈消耗。 必须按最深合法路径核算。

重入与共享状态

嵌套 ISR 可能再次访问共享数据或调用相同函数。 必须审查重入安全性、原子性和共享状态保护。

HRTOS 的中断嵌套路径应按实际支持的优先级关系、入口机制和退出机制分析， 而不是假定所有中断都可以无限嵌套。

05. 中断退出与任务调度

ISR 结束后，处理器可能返回被中断的执行路径，也可能在内核规定的条件下 进入任务调度或其他内核处理路径。 是否发生任务切换，取决于内核的调度机制和当前系统状态。

ISR Completion 完成本次中断处理
↓
Return Path 满足返回条件时恢复原执行路径
Kernel / Scheduling Path 符合内核条件时继续处理调度或上下文切换
↓
Next Execution 恢复原任务或执行内核选择的后续任务

对采用专门中断退出接口或汇编返回路径的内核， ISR 的退出方式属于内核控制流契约。 不能仅凭普通 C 函数返回的语义，推断其与内核中断返回机制等价。

对 HRTOS 的实际实现，应核对 ISR 入口方式、退出接口、 是否存在中断退出时调度，以及对应的上下文恢复顺序。 这些细节会直接影响正确性和时间分析。

06. 中断对实时性的影响

中断会占用处理器时间，也可能延迟任务执行或其他中断的响应。 因此，实时性评估既要分析单次中断路径，也要分析多个中断在目标时间窗口内 对任务执行造成的综合干扰。

  • 响应延迟：从请求发生到规定的响应起点之间的时间。
  • ISR 执行时间：中断处理路径实际占用的处理器时间。
  • 屏蔽时间：相关请求不能被接受的时间区间。
  • 嵌套开销：多层中断的入口、退出与上下文保护开销。
  • 任务干扰：中断执行使任务被推迟的时间及其对响应时间的影响。

这些指标的计算边界必须明确。例如，ISR 执行时间是否包含入口和退出代码， 会影响测量结果之间的可比性。

Real-time analysis must account for interrupt latency, handler execution, masking intervals, nesting overhead, and interference with task execution.

07. 中断路径的验证方法

中断行为需要结合静态代码分析、目标芯片上的测量与压力测试。 单次测量只能证明某次运行中的观测值，不能单独证明最坏情况上界。

静态路径分析

检查中断入口、寄存器保存、调用链、返回路径与条件分支， 识别可能增加执行时间的路径。

硬件时序测量

使用 GPIO、定时器或逻辑分析仪测量请求至响应、 ISR 执行区间及中断退出后的行为。

嵌套压力测试

在允许的中断组合下检查上下文完整性、最大堆栈占用 和共享数据保护。

边界条件验证

覆盖中断屏蔽、请求同时到达、连续触发和调度边界等情况， 检查事件是否丢失以及返回路径是否正确。

若进一步开展最坏情况执行时间（WCET）分析， 应将反汇编指令周期、分支路径、芯片时序和中断干扰纳入统一模型， 并明确分析结论适用的配置与边界条件。

语义总结

中断流不只是 ISR 的执行顺序，而是从事件请求、硬件响应、 上下文保护到退出与后续执行的完整控制路径。

对 8051 实时操作系统而言，可靠的中断机制必须同时满足正确性与可分析性： 既要保证中断前后执行状态得到正确处理，也要能够明确响应延迟、 执行开销、嵌套边界和资源消耗。

A reliable interrupt model requires correct control flow, safe context handling, bounded nesting, and analyzable timing behavior.
